# v0.8.0 — Recovery Core

Дата: 2026-10-08

Основа: полная ветка v0.7.1 (`a7ccb67`), включая её исправления времени, ролей, отчётов и интерфейса. Предыдущие изменения сохранены.

## Ядро и деньги

- Транзакционная идемпотентность создания расходов, аренды, коммунальных платежей и зарплатных корректировок. Квитанция, финансовый журнал и аудит фиксируются вместе или полностью откатываются; другой payload с тем же ключом получает 409.
- Ключ операции сохраняется в форме при неоднозначной сетевой ошибке. Повтор не создаёт новую проводку.
- Ревизии расходов, аренды и коммунальных обязательств отклоняют конкурентные изменения. Аннулированные проводки нельзя воскресить.
- Открытый расчёт зарплаты сбрасывается при изменении всех поддерживаемых входных данных, в том числе оплате во время DRAFT-расчёта и позднем завершении оплаченного визита. Guard не позволяет сохранить устаревший расчёт.
- Уже CALCULATED периоды при миграции переводятся в DRAFT для повторного расчёта по исправленной логике; CLOSED периоды и их строки не изменяются.
- Оплаты, возвраты, финансовые проводки PAYMENT/REFUND/SALARY и услуги завершённых визитов становятся неизменяемой историей. Восстановлен отдельный уникальный индекс исходной проводки PAYMENT; несколько возвратов по-прежнему разрешены.
- Платежи проверяются по идентификатору реально сохранённой строки, а не по метаданным количества изменений с триггерами. Денежные суммы проверяются до тиына, коммунальный расчёт использует Decimal.
- Смена статуса старой пересекающейся записи не пересоздаёт резервирования. Архивирование специалиста/услуг не мешает администратору завершить неизменяемый по времени визит.

## Telegram и восстановление

- Зависший финальный attempt завершает связанные уведомления/получателей кампании; ручной повтор согласованно возвращает их в очередь.
- Перед повтором проверяется актуальность напоминания и согласие клиента. Архивированному клиенту сообщение не доставляется.
- Очередь новых напоминаний исключает уже поставленные сообщения и упорядочена по сроку: первые 100 больше не блокируют следующие.
- Cron worker защищён арендой; устаревший запуск не меняет отчёт более нового. Сбой setMyCommands/setChatMenuButton не останавливает доставку, настройка повторяется отдельно и видна администратору.
- Статус уведомления о бронировании отражает принятие сообщения Telegram, а не создание записи в CRM.

## Интерфейс и проверка

- Восстановление экрана после React-ошибки, timeout и backoff входа в Telegram.
- CI: TypeScript, ESLint, unit/integration tests, production build, аудит production-зависимостей и UI desktop/mobile с сетевым сбоем расхода.
- Миграция 0013 добавляет поля/таблицы/ограничения без удаления пользовательских записей. Перед production — backup и проверка дублирующихся исходных проводок.
- Текущий runtime: Cloudflare Pages + D1 + существующий Telegram worker; адрес Mini App не меняется.

Проверено локально: 105 тестов, TypeScript, ESLint, production build, 13 миграций на изолированной D1/Miniflare, 22 экрана сотрудников и клиентские потоки в 1440/390 px. Аудит production-зависимостей: 0 уязвимостей. Браузерный сценарий отдельно проверяет одинаковый ключ расхода после сетевой ошибки.

Ограничения: Telegram доставляется at-least-once; редкий дубль после принятия сообщения и до фиксации D1 исключить нельзя. Повторы денег безопасны только с исходным ключом. Проверки не означают обещание абсолютной безотказности; порядок реагирования и отката описан в OPERATIONS.md.

# v0.7.1 — Audit Fixes

Дата: 2026-10-08

Независимый аудит v0.7.0 (API, схема, Telegram, роли, деньги, UI). Все найденные ошибки исправлены в этом релизе; данные существующей базы не переписываются.

## Исправлено: отчёты и время

- `/api/pnl`, `/api/kpi` и экспорт P&L/KPI падали или возвращали нули: число параметров SQL не совпадало с плейсхолдерами.
- Период `to=YYYY-MM-DD` исключал последний день в P&L, KPI и отчётах; экспорт CSV расходился с экраном. Все отчёты используют общий `periodRange()` с местными сутками центра (включительно).
- Сравнение дат строками ломалось на смеси старого формата `YYYY-MM-DD HH:MM:SS` и ISO: фильтры записей, ближайшие визиты, база зарплаты, дашборд, уведомления переведены на `julianday()`, API отдаёт канонический ISO.
- Смена статуса старой записи считалась переносом (повторная проверка расписания, новые напоминания, сообщение клиенту).
- Значения `datetime-local` сохранялись как UTC (10:00 в Алматы становилось 15:00): записи, отсутствия, расходы, аренда, коммунальные, задачи, follow-up, движения склада, цели.
- Дашборд считал месяц и «сегодня» в UTC; атрибуция зарплаты различалась между P&L, отчётами и дашбордом.
- Невалидные `from`/`to` в целях и KPI приводили к 500.

## Исправлено: роли и доступ

- Специалист получал суммы оплат и внутренние заметки клиентов в списке; администратор — зарплаты сотрудников, себестоимость услуг, расходы и зарплаты на дашборде, аренду/коммунальные и журнал аудита в уведомлениях.
- Архивная карточка клиента сохраняла доступ к кабинету и бронированию; теперь сессии связанного пользователя завершаются, API отвечает 403, кабинет показывает уведомление.
- `/api/auth/logout` требовал действующую сессию, поэтому просроченную или отозванную cookie нельзя было очистить.
- Cookie сессии `SameSite=Lax` не отправлялась из iframe Web Telegram; переведена на `SameSite=None; Secure`, проверка Origin сохранена.
- Повторное использование чужого ключа идемпотентности бронирования возвращало ошибку слота вместо 409.
- Интерфейс скрывает действия, недоступные роли (экспорт, создание, модерация, настройки), вместо ошибки после отправки.

## Исправлено: деньги, склад, записи

- Закрытие периода зарплаты с отрицательным итогом «тихо» пропускало строку ledger (`INSERT OR IGNORE`); теперь 409. Итоги считаются через `Decimal`, периоды не пересекаются и открываются по местным дням, ledger-запись датируется концом периода.
- Приём закупки сообщал успех при параллельном приёме, принимал черновики и не распознавал повтор после полного приёма; статусы `RECEIVED → DRAFT` закрыты, `paidAmount` и способ оплаты валидируются.
- Перенос записи клиентом перезаписывал услуги и цену по каталогу; теперь переносится только время, перенос многоуслужных записей запрещён.
- Редактирование сотрудника без списка филиалов удаляло все привязки филиалов.
- Правка аннулированного расхода снова проводила его в ledger; PATCH поставщика без `isActive` снимал архив.
- Кампании никогда не доставлялись: согласие `MARKETING` нигде не выдавалось. Согласие добавлено в анкету и профиль клиента, получатели фильтруются по нему.
- Шаблон `BOOKING_CANCELLED` не обновлялся миграцией 0009 (`INSERT OR IGNORE`), причина отмены не доходила до клиента.
- Триггер пересечений (0011) срабатывал на любую смену статуса; две старые пересекающиеся записи нельзя было подтвердить или завершить, webhook отвечал 500 и Telegram повторял update бесконечно. Миграция `0012` ограничивает проверку реальным изменением времени/специалиста; webhook отвечает понятным сообщением и фиксирует update.
- Экспорт `inventory` всегда падал (`p.active` вместо `is_active`).
- Старые записи стали нередактируемыми из-за обязательного телефона/показаний при смене только статуса.

## Безопасность и валидация

- Экранирование `%`/`_` в поиске, лимит длины `q`; ограничения длины сообщений кампаний, причин отмены, заметок, имён; лимиты размеров пакетов (позиции закупок, получатели, ключи прочтения).
- Проверка существования связанных сущностей (филиалы, сотрудники, исполнители, клиенты, сегменты, поставщики); целочисленные рабочие дни; Telegram ID только из цифр; телефоны через общий валидатор.
- Внутренние тексты ошибок D1 не возвращаются клиенту; 404 вместо 400 для отсутствующих сущностей; `/api/telegram/health` не раскрывает конфигурацию.
- CSP: `object-src 'none'`, `frame-ancestors` включает `webk.telegram.org` и `webz.telegram.org`; просроченные сессии пользователя удаляются при входе.

## Интерфейс

- Диалоги подтверждения в приложении вместо `window.confirm`/`alert` (отмена/неявка, удаление отсутствия, архив услуги, аннулирование расхода, закрытие периода, запуск рассылки, приём поставки).
- Состояния загрузки/ошибок и защита от двойного нажатия во всех формах; модальные окна не закрываются во время сохранения.
- Записи: выбор клиента с поиском и быстрым созданием нового клиента, оплата «QR / Kaspi», версии записей (`revision`) во всех изменениях.
- Финансы: даты по умолчанию, дата оплаты только для статуса «Оплачено», живой расчёт коммунального платежа; карточка обязательств вместо статического текста. Настройки: выбор рабочих дней кнопками, состояние системы из `/api/health`, перерывы в расписании.
- Клиентский кабинет: согласие на рассылки, уведомление об архивной карточке, состояния листа ожидания.
- Вёрстка: таблицы и действия без горизонтального скролла на 390 px, липкая шапка и баннер сети на мобильных, печать, кольца фокуса, контраст текста и статусов, 44px цели нажатия, светлая палитра в тёмной теме Telegram.
- Локализация смешанных англо-русских подписей (P&L, Net revenue, Retention, Follow-up, Snapshot и др.).

## Инфраструктура и проверки

- Миграция `0012_audit_fixes.sql` (триггер и шаблон; без перезаписи данных).
- `eslint-plugin-react-hooks`, `engines.node >= 22.13`, `npm run qa:ui`, `_redirects` для `/clients/*.txt`.
